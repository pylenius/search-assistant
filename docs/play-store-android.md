## Read this first: Play App Signing will break App Links

Play App Signing is mandatory for new apps. You upload an AAB signed with
`app/release.keystore`, but Google **re-signs it with its own key**, so
installs from Play carry a different SHA-256 than the one currently served in
`/.well-known/assetlinks.json`. If nothing is done, `/s/{slug}` links stop
opening the app for everyone who installs from Play — silently, with the link
falling back to the browser.

After the first upload:

1. Play Console → your app → **Test and release → Setup → App signing**
2. Copy the SHA-256 under **App signing key certificate**
3. Append it to `AndroidCertFingerprints` in
   `apps/api/SearchAssistant.Api/Endpoints/WellKnownEndpoints.cs`
4. Redeploy the API, then confirm:
   `curl https://searchassistant.eport.fi/.well-known/assetlinks.json`

The existing two fingerprints (local debug keystore, `release.keystore`)
should stay — they keep locally-built APKs verifying.

## Full description (≤4000)

```
Search Assistant keeps a group together on one map.

Picking mushrooms, walking a forest line, hiking with friends, or looking for
something someone dropped — everyone taps the same link, picks a name, and
immediately sees the same picture: the area you agreed to cover, where each
person is right now, and which ground has already been walked.

NO ACCOUNTS
There is no signup, no email, and no password. Creating a search gives you a
link. Anyone you send it to can join in seconds — from this app, or straight
from a phone browser if they'd rather not install anything.

DRAW THE AREA
Sketch a polygon on the map and it appears for everyone in the search within
a second. Name it, colour it, remove it when the group moves on.

SEE EACH OTHER LIVE
Turn on location sharing and your position streams to the rest of the group,
and theirs to you. Tap someone in the list to centre the map on them.

RECORD WHAT YOU'VE COVERED
Start recording and your walked track is drawn on the shared map, so the
group can see which ground is done and which is not — the single most useful
thing when several people sweep the same forest. Recording keeps running with
the screen off, and tracks can be exported as GPX.

SHARE HOWEVER YOU LIKE
Send the link in any messaging app, or show the QR code for someone to scan.

SEARCHES DON'T LINGER
A search expires on its own — by default a week after it's created — and the
person who started it can rename it, clear the recorded tracks, or delete the
whole thing at any time. Deleting removes every position, path, and area in
it.

PRIVACY
No ads, no analytics SDKs, no trackers, and nothing sold or shared with
anyone. Your location goes to the people in your search and nowhere else, and
only while you have sharing or recording switched on. A notification is shown
the whole time location is being collected. Full policy:
https://searchassistant.eport.fi/privacy
```

Screenshot order (Play shows them in this order):

1. `1-landing.png` — landing screen: create a search, recent searches
2. `2-map.png` — the sweep: search area, three walked tracks, four live positions
3. `3-participants.png` — participants sheet with last-seen times
4. `4-share.png` — share sheet with QR code and join link
5. `5-recording.png` — recording a track, with sharing active

Two format traps worth remembering, because they differ from Apple's:

- Play rejects images whose **longest side exceeds twice the shortest**. The
  Pixel 8 emulator's native 1080×2400 is 2.22:1 and would bounce; these were
  captured with `adb shell wm size 1080x1920` to get a true 9:16.
- Screenshots and the feature graphic must be **24-bit PNG without alpha**,
  while the store icon must be **32-bit PNG with** it. `adb exec-out
  screencap -p` produces RGBA, so the script converts.

No tablet or Wear screenshots — the listing targets phones only. Play will
still let the app install on tablets; add tablet screenshots later if that
matters.

## Data safety form

Answer **yes**, the app collects user data. Then declare exactly these, all
with **Collected: yes / Shared: no / Processed ephemerally: no /
Required: no (user-initiated)**, purpose **App functionality**:

| Data type | Play category | Notes |
|---|---|---|
| Approximate location | Location | Coarse permission is requested alongside fine |
| Precise location | Location | Only while sharing or recording is switched on |
| Name | Personal info | The self-chosen display name, not a legal name |
| User IDs | Personal info | Per-search session token; not tied to a person or device |
| Other user-generated content | App activity | Drawn areas and recorded paths |

Everything else is **not collected**: email, phone, address, financial info,
health, messages, photos, videos, audio, contacts, calendar, app activity
beyond the above, web browsing, installed apps, device IDs, crash logs,
diagnostics, and any advertising data.

Then:

- **Is all user data encrypted in transit?** Yes — HTTPS/WSS throughout.
- **Do you provide a way to request data deletion?** Yes. The search owner can
  delete a search from the app, which removes every position, path, and area
  in it. Every search also expires automatically (7 days by default).
- **Data used for tracking or advertising?** No, for every row.

Category: **Reference, News, or Educational**. Answer "No" to every violence,

## Foreground service permission declaration

Play requires a declaration for each `foregroundServiceType`. The app declares
exactly one, `location` (`FOREGROUND_SERVICE_LOCATION`):

```
The location foreground service runs only while the user has explicitly
switched on "Share location" or "Record path" inside a search. It streams the
user's position to the other people in that same search and draws the walked
track on the shared map, which is the core purpose of the app. The group needs
positions to keep updating while the phone is in a pocket with the screen off
— that is exactly when someone is walking their part of the search area.

An ongoing notification ("Sharing your location") is visible the entire time
the service runs, and the service stops as soon as the user turns sharing and
recording off or leaves the search.
```

Note the app does **not** request `ACCESS_BACKGROUND_LOCATION`, so no
background-location declaration or video review is needed. See below.

## Why there is no background-location declaration

`ACCESS_BACKGROUND_LOCATION` used to be in the manifest, but nothing ever
requested it at runtime — it was never granted, so it was never doing
anything. It was removed before this submission. Keeping it would have
triggered Play's background-location review (written justification plus a
video demo, and a common source of rejections) for a permission the app
doesn't use.

Screen-off recording still works, because a foreground service with
`foregroundServiceType="location"` started from a visible screen keeps
location access under ordinary while-in-use permission. Verified on an
emulator: with the app backgrounded and the screen off, injected fixes
continued to reach the server.

## Before you upload

1. ~~Bump the version.~~ Done — `versionName` is `1.0.0`, `versionCode` is
   `1`. **Bump `versionCode` on every subsequent upload**; Play rejects a
   repeat.
2. **Build the bundle** (not an APK — Play needs an AAB):
   ```sh
   cd apps/android && ./gradlew bundleRelease
   # -> app/build/outputs/bundle/release/app-release.aab
   ```
   Requires `local.properties` with `MAPS_API_KEY`, `RELEASE_KEY_ALIAS`,
   `RELEASE_STORE_PASSWORD`, `RELEASE_KEY_PASSWORD`, and
   `app/release.keystore` present. Without the keystore the build silently
   falls back to the debug key — check before uploading.
3. **Sanity-check the artifact's permissions** — an added dependency can
   quietly merge new ones in (zxing added `CAMERA` once already):
   ```sh
   $ANDROID_HOME/build-tools/*/aapt2 dump permissions \
     app/build/outputs/apk/release/app-release.apk
   ```
   Expected: INTERNET, ACCESS_COARSE_LOCATION, ACCESS_FINE_LOCATION,
   FOREGROUND_SERVICE, FOREGROUND_SERVICE_LOCATION, POST_NOTIFICATIONS,
   ACCESS_NETWORK_STATE. Nothing else.
4. **Maps API key.** The release build embeds whatever `MAPS_API_KEY` is in
   `local.properties`. Make sure that key's Google Cloud restrictions list the
   **release** signing SHA-1 (and, once Play App Signing is on, the Play app
   signing SHA-1) or the map renders blank for real users.
5. **Upload** to Internal testing first, install from Play on a real device,
   and confirm the map draws and `/s/{slug}` links open the app.
6. **Then fix assetlinks** with the Play signing key — see the top of this doc.
